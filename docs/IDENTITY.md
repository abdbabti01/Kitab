# Identity, Authentication & Security track

The fourth track: 12 units (`/learn/identity`), the Identity Playground (`/practice/identity`), the Token Inspector
(`/practice/identity/tokens`), the Authorization Playground (`/practice/identity/authorization`), 13 Practice challenges
(`/practice/identity/challenges/:id`), 8 guided experiments and 13 Engineering Labs (`/lab/identity/:id`). Everything
lives in `src/identity/`, plus `src/lab/labs/identity.ts` and `worker/identity-lab.ts`. Standards and their status:
[IDENTITY-STANDARDS.md](IDENTITY-STANDARDS.md).

**Division of labour with System Design.** The System Design security unit (`/learn/system-design/security`) teaches
where identity sits in an architecture and links here. This track teaches the protocols themselves: every message,
parameter, token and check, how each fails, and how to implement them.

## Layers

```text
model.ts         FlowEvent / Check / StateChange / Scenario; runScenario, parseConfig (untrusted → config),
                 firstFailure, outcomeOf, stateAt (fold), flow() builder (stops after a failed check)
flows/*.ts       ten scenarios, each run(config) → one canonical event stream
sha256.ts        sync SHA-256 + base64url, so PKCE challenges in the engine are real RFC 7636 values
authz.ts         deny-by-default policy engine: authenticate → valid → audience → scope/role → tenant →
                 ownership → conditions; securePolicy, audit (suite judged against it)
jwt.ts           real Web Crypto (ES256, RS256): decode, sign, tamper, validate (stops at first failure)
content/         twelve units on the System Design ConceptUnit shape + walkthrough, examples, labs, related, sources
code.ts          C#, Java, Python examples (verified by scripts/verify-identity-examples.ts)
cycles.ts        guided experiments on src/learning/cycle.ts (answers read from the run)
challenges.ts    classify / diagnose / configure / policy / decision; judge()
progress.ts      kitab.identity.v1 via keyed-store: units, challenges, last Playground scenario
catalog.ts       ids, titles, versions only (always loaded by the track pages)
ui/              lazy pages: IdentityPlayground, TokenInspector, AuthorizationPlayground, IdentityUnitPage,
                 ChallengePage; Trace.tsx (sequence, inspector, state, playback, workbench), CodeExamples
lab-fixtures.ts  public JWK + pre-signed synthetic lab tokens (generated by scripts/identity-lab-fixtures.ts)
```

**One event stream.** A run is `FlowEvent[]`. The sequence diagram, the message inspector, the state panel
(`stateAt` folds every event's `sets`), the outcome banner (`outcomeOf`), the lesson walkthroughs, the guided experiments
and the challenges all read that array. No view keeps a second model. Each event records sender, receiver, kind,
channel (front: through the browser; back: direct HTTPS; internal), method, endpoint, status, headers, parameters,
tokens, checks (with values and the rule they come from), state changes, purpose, what protects it, what happens if a
check fails, and what comes next. `flow()` stops a scenario at the first failed check and adds only its consequence,
as a real implementation would.

## Scenarios

| Scenario | Standards | Settings and faults |
|---|---|---|
| Sign in with OpenID Connect | OIDC Core §3.1, RFC 6749 §4.1, 7636, 9700, 10017, 9207, 6750 | web/BFF or browser client; IdP session; API call; PKCE; consent; redirect URI; state, verifier, code reuse, nonce, ID token aud/expiry/key, access token aud/scope, ID token sent to the API |
| Single sign-on across two applications | OIDC Core, RP-Initiated Logout, Back-Channel Logout | IdP session valid/expired; MFA step-up; extra scopes (consent per client); local logout, IdP logout, back-channel logout, app session expiry; ID token replayed to the other app |
| Service to service (Client Credentials) | RFC 6749 §4.4, 7523, 8705, 8707, 9068 | secret, private_key_jwt, mTLS; scope not granted; wrong resource; cached token used after expiry |
| Sign in on a TV (Device Authorization) | RFC 8628 | approve, deny, never (expired_token); polling too fast (slow_down) |
| Refresh tokens, rotation and reuse | RFC 6749 §6, RFC 9700 §2.2.2, §4.14 | rotation on/off; stolen refresh token used before or after the app |
| Opaque tokens, introspection and revocation | RFC 7662, 7009 | revoke between calls; introspection cache |
| Enterprise SSO with SAML 2.0 | SAML 2.0 Core, Bindings, Profiles; XML Signature | SP- or IdP-initiated; unsigned, rotated certificate, audience, expired, InResponseTo, replay, signature wrapping |
| MFA factors and a phishing proxy | NIST SP 800-63B, WebAuthn L3 | TOTP, SMS, push with number matching, passkey; real site or adversary-in-the-middle proxy |
| Passkeys: the WebAuthn ceremonies | WebAuthn Level 3 (Recommendation, Aug 2026) | registration, authentication; wrong origin, reused challenge, no user verification, unknown credential |
| Signing key rotation and JWKS refresh | RFC 7517, OIDC Core §10.1.1 | graceful or abrupt rollover; refetch on unknown kid or pinned keys; attacker kid |

`tests/identity-engine.test.ts` runs **every combination of every control** of every scenario (over a thousand runs)
and checks determinism, bounds (≤ 60 events), declared actors, ordered time, a purpose per event and the stop-after-
failure rule; then each fault against the exact check that must catch it.

## Real versus modelled

| Where | Real | Modelled |
|---|---|---|
| Playground scenarios | PKCE challenges (SHA-256 computed); every parameter name and rule from the cited specs | Signatures (tracked by key id and checked against the keys a verifier trusts), networks, identity provider internals |
| Token Inspector | Keys generated per visit with Web Crypto; ES256 and RS256 signing and `crypto.subtle.verify`; claim checks | Nothing: the tokens are synthetic but the cryptography is real. Keys and tokens are never stored or sent |
| Authorization Playground | The policy engine is the thing being taught | Fixed people and orders |
| Code labs | The learner's JavaScript runs in the sandbox; PKCE, JWKS and challenge-response labs use Web Crypto | Identity providers (stand-in functions) |
| HTTP lab | Real requests to `worker/identity-lab.ts`, which verifies RS256 signatures with Web Crypto | A teaching resource server with fixed data and pre-signed tokens |
| WebAuthn | — | A conceptual walkthrough. Kitab never calls `navigator.credentials` and never asks to create a passkey |
| C#, Java, Python | 7 examples built and run, output compared; 8 built (they need a real identity provider) | Keys and tokens inside the runnable examples come from a labelled stand-in in the same program |

## Practice

| Kind | Judged by | Challenges |
|---|---|---|
| classify | authored answers per item | Authentication or authorization? |
| diagnose | the engine's first failed check (or, for sessions, the step that explains the redirect); pass/fail marks are hidden in the trace | Investigate a redirect after a session expires · Validate an ID token · Why did the API reject the token? · Diagnose a SAML login failure · Triage identity incidents |
| configure | requirements checked against the engine's run of the learner's settings | Repair a broken sign-in flow · Set up SSO for two applications |
| policy | `audit()`: no request wrongly allowed or refused | Fix an API authorization policy · Secure a multi-tenant API |
| decision | `judgeDecision` (acceptable choice, only relevant reasons, enough of them) | Configure OAuth correctly · Stop a phishing proxy · Design an enterprise identity architecture |

Several challenges accept more than one solution where that is technically right (for example a public client can be
fixed with PKCE or by moving to a backend-for-frontend; scope already mirrors roles in the policy suite, so a policy
without the role rule also passes). A challenge completes on its first pass and is mastered after passes in two
different variants. Opening or reading records nothing. Tests prove, for every variant, that the right answer passes
and a wrong one fails, and that each broken starting point fails.

## Progress (`kitab.identity.v1`)

Through `src/learning/keyed-store.ts`: units (`answers`, `completedAt`, never un-completed), challenges (version,
attempts, variants passed, `passedAt`, `masteredAt`) and `prefs.playground` (scenario id and at most 12 validated control
values). Never stored: tokens, passwords, keys, protocol traces. Guided experiments use `kitab.experiments.v1` like every
other subject. Engineering Lab drafts (`kitab.engineering-labs.v1`) now drop credential header values
(Authorization, Cookie, Proxy-Authorization, X-Api-Key) unless the value is one of the lab's synthetic tokens, so a real
token typed by mistake is never saved. No existing key, id or record format changed.

## Threat model and security controls

- **No real credentials anywhere.** All users, keys and tokens are synthetic; hosts are under `.example`
  (RFC 2606). Pages that accept free-form tokens (Token Inspector) process them locally, never send, log or store them,
  and warn against pasting real ones.
- **`/api/lab/identity/*` (worker/identity-lab.ts)** — GET only; no storage, D1, AI or outbound requests; inputs
  bounded (token ≤ 4 KB, numeric ids); responses JSON with `nosniff` and `cross-origin-resource-policy: same-origin`;
  cross-site browser requests refused (shared `handleLab`). It issues nothing: the private key that signed the fixtures
  was discarded at generation (only the public JWK is in the repository). A token whose header doesn't name the lab
  key is refused before its payload is decoded, and no token value or claim is ever reflected — it is not a
  verification oracle for real tokens. The echo endpoint already withholds credential header values.
- **Sandbox.** Unchanged boundary (opaque-origin `<iframe sandbox="allow-scripts">`, CSP without network, Worker
  inside). Chromium gives that Worker no `crypto.subtle` (it isn't a secure context); the frame, which has one, runs an
  allowlist of six Web Crypto operations for its own Worker (digest, generateKey, importKey, exportKey, sign, verify),
  at most 5,000 per run. `CryptoKey` exists only in secure contexts, so keys stay in the frame (at most 1,000 per run)
  and the Worker receives handles describing them, swapped back for the real key on the next call. Requests and results
  never reach Kitab's page. Browser tests run the PKCE, JWKS and challenge-response labs there: starters fail their
  tests, solutions pass.
- **Rendering.** Claims, assertions and headers are rendered as React text (never as HTML); a browser test signs a
  token whose claim contains an `<img onerror>` payload and checks nothing is injected.
- **Production posture.** Kitab's own authentication and security headers are untouched; no account system, identity
  provider or paid service was added.

## Accessibility and layout

The run's three views (Sequence, Message, State) sit side by side on wide screens and become tabs below 760 px. Every
message is a button with a full description (sender, receiver, title, failed check); later messages are rendered only
when reached, so predictions aren't given away. Playback has labelled buttons and a polite live position. The message
list scrolls itself to the current step, never the page. Selects are named by their visible labels. Reduced motion
needs nothing extra (no animation is required to follow a run). All identity pages were checked for horizontal overflow
at 320, 390, 768, 1024 and 1440 px.

## Known limits

- Signatures in the Playground are modelled; real verification is in the Token Inspector and labs.
- Front-channel logout, OIDC Session Management, PAR, DPoP flows, token exchange, SAML SLO, encrypted assertions and
  attestation are explained in lessons, not simulated.
- Vendor content (Entra ID, Auth0, Okta, Keycloak) is conceptual: no console click-paths, no real tenants.
- Scenarios cover chosen cases with fixed identifiers, not every possible deployment.
- Challenges are formative and judged in the browser: a determined learner can forge results.
- The HTTP lab's tokens carry `exp` in 2099 (except the expired one) and a key that can never sign again.
